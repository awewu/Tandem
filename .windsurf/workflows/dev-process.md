# 瑞美HVAC AI - 软件开发流程管理

## 🎯 开发原则

- **质量优先**: 所有代码必须通过质量门禁才能合并
- **自动化**: 重复性任务必须自动化
- **透明化**: 进度和问题对所有干系人可见
- **快速反馈**: 问题早发现早解决

---

## 📅 Sprint周期 (2周)

```
Week 1: 开发冲刺
  周一: Sprint规划会 (2小时)
  周二-周五: 开发 + 每日站会 (15分钟)
  
Week 2: 测试交付
  周一-周三: 功能完成 + 自测
  周四: Code Review + Bug修复
  周五: 演示 + 回顾会 (1小时)
```

### 每日站会模板

```
昨日完成:
- 任务A: 完成度80%

今日计划:
- 完成任务A
- 开始任务B

阻塞问题:
- 需要XX资源支持
```

## 🚪 质量门禁 (Quality Gates)

### L1 - 代码级门禁 (pre-commit)

```bash
# 自动执行
npm run lint       # ESLint检查
npm run format     # Prettier格式化
npm run type-check # TypeScript检查
```

**标准**: 0 Error, Warning < 10

### L2 - 单元测试门禁 (pre-push)

```bash
npm run test:unit  # Jest测试
```

**标准**: 
- 覆盖率 > 80%
- 所有测试通过
- 新增功能必须有测试

### L3 - 集成测试门禁 (CI/CD)

```bash
npm run test:integration
npm run test:api
```

**标准**: 
- API测试100%通过
- 响应时间 < 200ms

### L4 - 性能门禁 (Nightly)

```bash
npm run test:performance
```

**标准**:
- P95响应时间 < 100ms
- 内存使用 < 512MB
- 并发支持 > 1000 RPS

## 🔄 分支策略 (Git Flow简化版)

```
main        ─────────●─────────●───────── 生产分支
                       │         │
release/v4.1 ──────────●─────────●──────── 发布分支
                      /         /
feature/ai-consultant ●────────●─────────── 功能分支
                     /
develop   ───────────●───────────────────── 开发分支
```

### 分支规范

| 分支类型 | 命名规范 | 来源 | 合并目标 |
|----------|----------|------|----------|
| 功能分支 | `feature/功能描述` | develop | develop |
| 修复分支 | `fix/问题描述` | main | main + develop |
| 发布分支 | `release/v版本号` | develop | main |
| 热修复 | `hotfix/问题描述` | main | main + develop |

## 📝 代码审查 (Code Review)

### 审查清单

**功能正确性**
- [ ] 需求实现完整
- [ ] 边界条件处理
- [ ] 错误处理完善

**代码质量**
- [ ] 符合编码规范
- [ ] 命名清晰有意义
- [ ] 函数长度适中
- [ ] 复杂度可控

**可维护性**
- [ ] 必要注释
- [ ] 文档更新
- [ ] 测试覆盖

**性能安全**
- [ ] 无性能陷阱
- [ ] 无安全风险
- [ ] 资源释放正确

### 审查流程

```
1. 开发者提交PR → 关联Issue
2. 自动检查触发 (CI) → 必须通过
3. 指派Reviewer (至少1人)
4. Reviewer审查 → 批准/请求修改
5. 修改后重新审查
6. 合并到目标分支
```

## 🚀 部署流程

### 环境定义

| 环境 | 用途 | 触发条件 | 审核 |
|------|------|----------|------|
| Dev | 开发自测 | 自动 | 无需 |
| Staging | 集成测试 | PR合并后 | 自动 |
| Pre-prod | UAT测试 | 发布分支 | 需要 |
| Production | 生产 | 手动 | 必须 |

### 部署检查清单

**部署前**
- [ ] 所有测试通过
- [ ] 版本号更新
- [ ] 变更日志更新
- [ ] 数据库迁移脚本就绪
- [ ] 回滚方案确认

**部署中**
- [ ] 蓝绿部署/金丝雀
- [ ] 监控指标正常
- [ ] 健康检查通过

**部署后**
- [ ] 核心功能验证
- [ ] 监控告警检查
- [ ] 用户反馈收集

## 🆘 应急响应

### 故障等级

| 等级 | 定义 | 响应时间 | 解决时间 |
|------|------|----------|----------|
| P0 | 系统不可用 | 15分钟 | 2小时 |
| P1 | 核心功能故障 | 30分钟 | 4小时 |
| P2 | 非核心功能故障 | 2小时 | 24小时 |
| P3 | 体验优化 | 24小时 | 下次迭代 |

### 应急流程

```
1. 发现 → 立即上报到值班群
2. 评估 → 确定故障等级
3. 响应 → 启动应急预案
4. 修复 → 记录处理过程
5. 复盘 → 24小时内完成
```

## 📈 持续改进

### 迭代回顾会议

**每Sprint一次，1小时**

议程:
1. 数据回顾 (15分钟)
   - Sprint目标达成率
   - 计划vs实际
   - 质量指标

2. 做得好的 (10分钟)
   - 团队分享
   - 成功经验

3. 做得不好的 (15分钟)
   - 问题识别
   - 根因分析

4. 改进措施 (15分钟)
   - 行动项
   - 负责人
   - 截止时间

5. 庆祝 (5分钟)
   - 认可贡献
   - 团队建设

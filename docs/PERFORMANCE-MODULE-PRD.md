# 绩效—薪酬一体化模块 PRD（设计原则 + 领域模型）

> 状态：草案 v0.1（仅设计，不含实现代码）
> 范围：瑞合瑞德集团 2026 增值分享激励体系的系统化落地
> 一句话定位：把"绩效评估 → 职级/薪资联动 → 增值分享结算"打通为一条**可计算、可举证、可自主把握**的端到端闭环。

---

## 0. 名词与缩写

| 缩写 | 含义 |
|---|---|
| **AIP** | 专才/成长者激励政策（P1–P4, M1） |
| **MIP** | 经营者/责任人激励政策（P5, M2–M4, BP） |
| **SIP** | 猎手/创收者激励政策（销售/售后/零售） |
| **LIP** | 蓝领/一线激励政策（工厂一线岗位） |
| **公允线** | 预算/目标规划线。线下=基本保障，线上=增值分享 |
| **增值分享** | 公允线之上真实创造价值的分享，非禀赋 |
| **FP&A** | 财务计划与分析（实际 vs 预算的权威数据源） |
| **BSC** | 平衡计分卡（KPI 底线数据体系） |

## 1. 核心精神：反禀赋（No-Entitlement）

> **奖金不是天生就有的，是员工自己干出来的。** 我们营造"创造价值、赢得尊重、快乐工作"的增值分享氛围。

四条不可动摇的第一性原则：

- **P1 守底线才有资格**：所有人先守住 BSC/KPI 底线；达不到预算规划，只有基本工资，不进入绩效与奖金。股东、员工同守底线。
- **P2 公允线之上才有分享**：`地板保障（线下） + 分享创造（线上）`。公允线由 FP&A/BSC 指标设计模拟"好的公允关系"。
- **P3 分享的是真实兑现的增量**：分享必须挂真实、已兑现、可归因的价值（利润超预算、开票回款、效率改进、质量损失下降），绝不分享未兑现的空头。
- **P4 员工是自己收入的第一责任人**：规则前置、人人可算、进退自主（双轨轮动 + What-if 模拟器）。

> **文化提示（叙事红线）**：系统对外话术永远是"你创造了多少可分享的价值"，而非"你被扣了多少"。未达线=**没有共同做出可分享的增量**，不是惩罚。

## 2. 三层引擎架构

```
┌─────────────────────────────────────────────┐
│  L3 结算层 Settlement                          │
│  职级变更→薪资重算→任务承接→增值分享结算→发放     │
├─────────────────────────────────────────────┤
│  L2 规则层 Policy-as-Data（按族可配，绝不写死）    │
│  公允线 / 触发阈值 / 职级带宽 / 分享公式 / 兑现规则  │
├─────────────────────────────────────────────┤
│  L1 数据层 Evidence（唯一真相源）                 │
│  BSC/KPI · OKR 达成 · FP&A 实际vs预算 · MES/质量   │
└─────────────────────────────────────────────┘
```

- **L1 数据层**：薪资从数据派生 → **数据不公则薪酬不公**。数据血缘、口径冻结（snapshot）、异常审计是一等公民。
- **L2 规则层**：所有阈值/公式/带宽以数据形式配置，四族独立参数化。
- **L3 结算层**：纯函数式，输入(数据+规则)→输出(可解释的薪酬结果+审计轨迹)。

## 3. 二维设计：四族人格 × 三层引擎

四族人格是激励设计的核心分野；"四个满意"是文化底色，非强对应关系。

| 族 | 地板（线下保障） | 分享乐器（线上创造） | 越线创造的价值 | 数据源 | 任务工资兑现 |
|---|---|---|---|---|---|
| **LIP** | 基本工资（主） | 系数上浮（小） | 效率改进 / 质量损失下降 | MES / 质量损失额 | —（另一套：部门基数×系数×出勤） |
| **AIP** | 固定含任务工资（厚） | 季度激励 + S1池（中） | 专业交付 / 战略专业支撑 | OKR落地 / 专业里程碑 | **固定全额**（成长者安全承诺） |
| **MIP** | 基本工资（薄） | 增值池 份数×分值（大） | BU 实际利润超预算 | FP&A 实际vs预算 + OKR分值 | **弹性对赌**（<70%全扣，年度回补） |
| **SIP** | 固薪三段（中） | 提成（上不封顶） | 越目标线的开票回款 | ERP/CRM 动销·回款·达成率 | 目标承接量定档 |

## 4. 薪资三段结构（AIP/MIP/SIP 白领与销售序列）

固定薪资 = 三个语义独立的 component，各回答一个不同问题：

- **基准工资 = "你是谁"**：按职级 + 核心履职能力核定，入门尊严线。
- **第三段工资 = "你扛什么位子/什么深度"**（名字随序列变）：
  - 管理序列（MIP）→ **职务工资**（管理职责/幅度）
  - 专业序列（AIP）→ **职级工资**（专业深度/等级）
  - 销售·服务（SIP）→ **专业工资**（能力认证，考试驱动）
  - 零售 → **技能工资**（考试驱动）
- **任务工资 = "你背多大的目标/多难的市场"**：`f(担当量)`，担当量因族而异——
  - AIP：项目难度 × 工作量
  - SIP：目标承接量
  - MIP：职责范围
  按"承诺 100% 达成"预付信任，非禀赋（MIP `<70%全扣` 即证：承诺未兑现，预付收回）。

> **LIP 不走三段**：固定工资为计时/岗位工资，奖金走 `部门基数×系数×出勤`。

### 4.1 薪酬表数据模型（解码 `薪酬结构总表.xlsx` + `各职能岗位技能工资对应表.xlsx`）

两张源表精确咬合，共同定义**固定月薪（不含绩效）**：

**定位键**：`岗类(Ⅰ/Ⅱ/Ⅲ类) × 层级(L1/L1A/L2/L3/L4/L5)` + 岗族 + 岗位学历 + 岗位经验。

**三段固定薪资的精确来源**：

- **基本工资 = f(岗位学历, 岗位经验区间)**：地板"你是谁"。取值 `{4400(0–3y), 4800(3–5y), 5600(5–10y), 6600(10y+)}`。
- **技能工资 = Σ(该层级必备技能的技能工资标准)**（A 轨核心）：**不是拍脑袋的带宽数字，而是"已认证技能定价之和"**。每项技能在 `技能工资对应表` 有单价（元）+ 必备等级(V)；**合计行 = 薪酬总表的"技能工资"列**，两表咬合。
- **任务工资 = f(岗类 × 层级 × 任务档 A–G)**（B 轨核心）：含 `任务比例 / 任务级差 / 调整级差`；**A–G 是围绕标准值以"调整级差"步进的 7 档承接档位**，对应员工承接的担当量。

**派生**：`月薪标准 = 基本 + 技能 + 任务`；`标准年薪(不含绩效) = 月薪 × 12`；`占比(基本·技能·任务)` = 反禀赋结构比。

**关键洞察（进模型）**：

- **能力定价表是 HR 动态维护的活体系（唯一真源）**：技能单价、必备等级、增删技能均由 HR 在治理台按需更新并**版本化**（`SkillMatrixVersion`），不是一次性固化的静态源数据。
- **技能工资恒为派生值**：`某等级技能工资 = Σ 该等级必备技能的当前生效定价`；`员工技能工资 = Σ 已认证且当前层级必备的定价`。**系统永不独立存一个会漂移的"合计"**——认证一项技能=加多少钱、改一次定价=谁的工资变，全部实时重算（What-if 与成长看板同源）。
- **标准来源即证据类型**：`案例佐证`（内部实证）/ `市场定价`（外部硬资格，如 CSCP、注安证书）。
- **薪酬总表"合计行"= 历史快照，非真理**：导入时它与"实时 Σ 定价"的差异（如 电控系统 `1100/1900/1700/…`、EHS `350/550/850`、设计 `0/0/150/300`）**是正常现象**（HR 事后调过价/快照过期），仅作**导入参考差异**提示 HR，**不是阻断错误、不设冻结闸门**。HR 在定价治理台调价即消解差异。

## 5. 双轨轮动机制（公平公允 + 员工自主）

基于既有"职级 ↔ 对应薪资"带宽体系，两个手柄由员工自己摇：

- **轨道 A — 能力/职级轨（纵向，会升会降）**
  职务/职级/专业**不是入职定死**，而是 **OKR 述职的效用结果**：述职好→职级升→工资升；述职差→**职级降→工资降**。连"你是什么水平"这段薪资，每年都要重新挣一次。
- **轨道 B — 责任/担当轨（横向，看你扛多重）**
  任务工资 = 你选择承接的担当量。敢接更难/更多/更宽，任务工资更高。

**轮动弹性**：职级即使降了，可靠 B 轨多接担当补位——这是"轮动"的出口，也是"员工自己把握收入"的落地。

**任务工资承接周期**（已定）：

- **默认年度承接**（AIP/MIP 等在年度述职节点承接）。
- **SIP 季度加档**：销售季度可重新承接目标、加档。
- **其他族半年加档**：在半年述职节点可调整承接。
- **特殊申请通道**：临时接大项目/大目标时，可发起特殊承接申请，审批通过后即时加档并留痕。

**职级↔薪资带宽模型**：
```
GradeSalaryBand {
  序列: AIP | MIP | SIP,
  职级,               // A1..A4 / P5 / M2..M4 ...
  基准工资,
  第三段工资,          // 职务/职级/专业/技能, 随序列
  任务工资档           // 含难度/承接量系数
}
```

### 5.1 能力轨（A 轨）的载体：岗族技能矩阵（Skill Matrix）

轨道 A 的"职级"不是抽象数字，而是**岗族技能矩阵**认证出来的等级。数据源：`docs/各职能岗位技能等级.xlsx`。它是**第三段工资（职级/专业/技能工资）跨序列的统一底层载体**。

**结构（五大职能板块 → 岗族 → 技能库）**：

- 五大板块：HR / 财务 / 生产 / 研发 / 营销 职能。
- 每板块含多个**岗族**（如财务：出纳/核算/成本/总账/FP&A）。
- 每岗族有**技能库**（具名技能）与**等级列 L1 / L1A / L2 / L3 / L4 / L5**。
- 每项技能标注**在哪些等级为必备（V）**，高等级是低等级技能的**超集（累加）**。
- 每项技能有**标准来源**：`案例佐证`（内部实证）或 `市场定价`（外部硬资格，如 CSCP 证书、高阶 Excel）。

**关键特性**：

- **岗族天花板差异化**：出纳仅到 L1，HRBP/开发/DT 到 L5 → **A 轨上升空间因岗族而异**（直接影响 §10 HR 预算的晋升 headroom）。
- **职级 = 满足的最高等级列**：员工在某岗族的职级 = 其"该列全部必备技能均通过标准来源认证"的最高 Lx。
- **升级 = 补齐下一列缺失技能 + 通过标准来源认证**；**降级 = 当前等级某必备技能不再达标 / 述职未过**。

**领域模型（新增）**：
```
SkillMatrix {
  职能板块: HR | 财务 | 生产 | 研发 | 营销,
  岗族,                              // 如 FP&A / 开发 / 质量
  可达等级: (L1|L1A|L2|L3|L4|L5)[],   // 岗族天花板差异化
  skills: SkillDef[]
}
SkillDef { 名称, requiredAt: 等级[], 标准来源: '案例佐证' | '市场定价' }
GradeCertification {
  employeeId, 岗族, 当前等级,
  已认证技能: { skillId, 证据(evidenceSnapshot), 认证时间 }[],
  下一级缺口: skillId[]               // 驱动 What-if 与晋升路径
}
```

**接锚三处**：

- **接薪资（§4）**：技能等级 Lx → 第三段"职级/专业/技能工资"档位；等级升→工资升，即 A 轨薪资联动。
- **接述职（§6）**：**述职 = OKR 结果（潜力/战略牵引）+ 技能等级复核（能力认证）** 双维；技能矩阵+案例佐证 = 述职的**客观锚**，破解"述职纯主观变政治"。
- **接 What-if（§9）**：`GradeCertification.下一级缺口` 直接告诉员工"再补齐哪几项技能→升级→职级工资 +X"，把成长路径变成可触摸的方向盘。

### 5.2 职级技能明示化 + HR 治理

**原则**：员工是自己成长的第一责任人——**看得见方向才谈得上自主**；标准要能被 HR 持续更新，但更新必须公平、可举证、不搞"暗改门槛"。分两个面：

#### A. 员工侧：技能成长看板（Skill Growth Board）— 实时可见的进步方向

- **我的定位**：岗族 · 当前等级 · 岗族天花板（明示"我这个岗族最高能到 Lx"）。
- **技能雷达**：按等级列展示 已认证 / 未认证 技能。
- **下一级缺口清单（核心）**：还差哪几项技能、每项要求的**标准来源**（案例佐证 / 证书如 CSCP）、以及**推荐学习资源**（接学院 `lib/learning` → 技能缺口关联课程）。
- **升级收益预览**：接 What-if（§9），"升到 Lx → 职级工资 +X"。
- **认证进度与证据提交入口**：上传案例/证书 → 写入 `GradeCertification.已认证技能.证据`。
- **述职节点提醒**：接 §6 闸门，倒计时与待办。

> 由此闭环：**技能缺口 → 学院课程 → 学完 → 提交案例佐证 → 认证 → 升级 → 加薪**，把成长、学习、薪酬串成一条员工自驱的链。

#### B. HR 侧：技能矩阵治理台（Skill Matrix Admin / CMS）— 定期更新政策与要求

- **版本化**：`SkillMatrixVersion { version, effectiveFrom, publishedBy, changelog }`——每次更新是一个可追溯版本。
- **定期更新周期**：如年度/半年 review 更新技能库与等级要求。
- **变更审批流**（对齐 LIP 政策"标准调整"条款）：HRBP 提案 → 体系副总审批 → 邮件报备 → **提前向员工公示**。
- **公平红线：变更公示 + 不溯及既往**：
  - 新要求设**生效日**、提前公示；
  - **已认证不因抬高标准而即时失效**（过渡期 / grandfathering），仅在下次述职按新版复核——避免程序不公与心理契约破坏。
- **认证锁版本**：员工认证依据"**认证当时生效的矩阵版本**"，与 `evidenceSnapshot` 同理冻结；标准抬高不追溯既往认证。
- **变更联动确认**：矩阵变更 → 触发受影响员工看板更新 + **知悉确认**（接 §6 `Acknowledgement`）。
- **复用**：可沿用学院 CMS 的 admin 模式（`app/admin/learning` 同构）。

**领域模型（新增）**：
```
SkillMatrixVersion { version, effectiveFrom, publishedBy, changelog, status: draft|published|archived }
// GradeCertification 增加：certifiedAgainstVersion  // 认证锁定的矩阵版本
```

## 6. 节点确认体系 + PIP 合规链

### 6.1 时间轴闸门（Cadence & Gates）

系统在时间轴预置确认闸门，每个闸门产出变化并要求员工在系统内确认：

- **季度 OKR 复盘（Q1–Q4）**：采集达成 → 生成"状态 + 趋势预警" → **知悉性确认**。
- **半年述职（H1/H2）**：职级 review = **OKR 结果（潜力/战略牵引）+ 技能矩阵等级复核（能力认证，§5.1）** 双维 → 升/维持/降 → **契约性确认**。
- **年度述职/结算**：年度职级定档 + 任务重新承接 + 增值分享结算。

### 6.2 职级变更状态机（PIP 合规链）

```
稳定 stable
  └─(Q达成<目标, 连续1季)→ 观察预警 watch        [知悉确认]
        └─(连续2季<目标)→ PIP触发 pip             [书面确认=PIP告知签署]
              └─ 改进期 improvement (第3季)
                    ├─(达标回升)→ 稳定 stable      [知悉确认]
                    └─(仍<目标)→ 降职生效 demotion [书面确认=降职/降薪生效签署]
                                     └─ 沿带宽下移一档 → 薪资重算
```

- **合规红线**：`连续两季<目标` 只触发 **PIP 告知 + 书面确认**，**不直接降薪**；必须再给**一个改进期**。此链对齐《劳动合同法》第 40 条"不能胜任 → 培训/调岗 → 仍不能胜任 → 才可调整"——改进期即法定"给机会"环节。
- **阈值按族可配**：`连续N季`、`低于目标口径`、`改进期时长` 全部参数化。

### 6.3 确认记录模型（证据链）

```
Acknowledgement {
  employeeId, nodeId, cycle,
  changeType: 知悉 | PIP告知 | 降职生效 | 职级晋升 | 任务承接,
  evidenceSnapshot,      // 当时 KPI/OKR 数据快照(冻结, 防事后争议)
  signatureState: 待签|已签|拒签|逾期视同送达,
  signedAt, appealState  // 申诉通道
}
```

- **两种法律性质**：知悉性确认（轻量）/ 契约性确认（电子签，具效力）。
- **`evidenceSnapshot` 冻结当时数据**是证据链命门——争议时还原"当时依据什么判"。

## 7. OKR 打分评估要求（自评 / 他评 / 上级 三源）

> 现状：系统已有 `自评(selfScore)` + `上级(managerScore)` + `终评(final = self*0.4 + manager*0.6)`。**缺 `他评(peer)` 维度**，本节明确补齐为 360 式三源合成。

### 7.0 OKR 与 KPI 的分工（先导 vs 滞后 → 潜力 × 绩效）

**这是整个评估体系的根节点，先立此再谈打分：**

- **KPI（BSC）= 滞后 / 结果指标**：守底线 + **绩效轴** + 奖金结算闸门。客观、数据驱动、向后看。
- **OKR = 先导指标 / 战略牵引**：衡量战略贡献与**员工潜力**，喂**九宫格潜力轴**与述职/职级轨（轨道 A）。向前看。
- **九宫格 = 绩效(KPI 结果) × 潜力(OKR 战略牵引 + 他评)**。
- **他评是潜力评估的优质维度**：同事视角最能捕捉 KPI 量化不了的**协作力、领导力、战略牵引力**等潜力信号——这正是他评权重高（40%）的深层理由：**它评的是潜力，不是结果复核。**

### 7.1 三评来源定义

- **自评（self）**：目标负责人在周期末自评，附**证据/复盘**（必填，无证据不予采信）。
- **他评（peer）**：由**协作相关方**（跨部门协作者 / 同级 / 内部客户）评分，**固定 4 位评议人各 10%**（半自选半指派），不足 4 人按 §7.2 缺维回退。用于捕捉**协作贡献**——对冲纯个体化对协作的侵蚀（SDT 关系性补丁）。
- **上级评（manager）**：直属上级评估，**必须书面理由**，尤其偏离自评时。

### 7.2 三源合成规则（基线权重 30/40/30，已定）

```
finalScore = self*0.3 + peer*0.4 + manager*0.3
他评 peer = 4 位评议人各 10%（Σ=40%）
```

- **基线方案**：自评 30% + 他人评议 40%（选 4 人，各 10%）+ 上级 30%。
  高他评权重刻意强化**协作文化**（SDT 关系性补丁），让"被同事认可创造了价值"直接进入薪酬。
- **逐族温和微调（已定，放开）**：因 OKR 评分测的是**潜力/战略牵引**（结果由 KPI 客观衡量），他评在各族都保留实质权重，微调仅在小范围浮动：
  - **AIP**：维持 30/40/30（协作产出，他评潜力信号最强）。
  - **MIP**：他评可略降、上级/董事会略升（经营担责的潜力更多由上层看见），如 30/30/40。
  - **SIP**：他评可温和下调（不砍到象征性），如 30/30/40。
- **他评反操纵护栏**（因 peer 权重高，必须配齐）：
  - **评议人半自选半指派**：员工提名一部分，上级/系统指派一部分，防"只选好友"抱团。
  - **去极值**：4 人评分**去掉最高、最低**再取均值（或异常值告警）。
  - **他评只评协作/贡献维度**，不评客观结果；必填简短理由，无理由不采信。
  - **匿名 + 互评对称监测**：识别"你高我也高"的互惠打分（logrolling）。
- **缺维回退**：有效评议人不足 4 人 → peer 维权重按实际人数比例并入 self/manager（保持归一）。
- **分歧闸门**：`|self − manager| > 0.3` → 强制进入**校准会（calibration）** 人工议定，留痕。

### 7.3 打分刻度（沿用 Google Re:Work，0.0–1.0）

- `0.7 = 达成预期（健康得分）`；`1.0` 罕见（moonshot 慎设）；`<0.4` 需深度复盘。
- 红黄绿：`≥0.7 green / ≥0.4 yellow / <0.4 red`（复用 `scoreBand`）。

### 7.4 反操纵护栏

- **每个量化闸门配一个定性复核**（述职/同行评审兜底），防 Goodhart。
- 目标用**区间**而非单点，降低 sandbagging 动机。
- **AI 只做证据聚合，不做打分裁决**；三评均需可追溯到 L1 数据。

## 8. 增值分享结算（L3）

- **触发条件（硬悬崖，已定）**：先过 P1 守底线闸门——**未达预算线即硬截断**，只发基本工资，绝不进入绩效与奖金结算。无缓坡、无解锁曲线（SIP 达成率≥80% 的解锁属其提成内部规则，不改变"未达预算线=无分享"的硬悬崖底线）。
- **MIP**：`池 = (实际−预算) × 族系数` → `个人 = 份数 × OKR分值 / Σ(份数×分值) × 池`。
- **SIP**：`提成 = 越线开票 × 品类系数`，达成率≥公允线解锁，预发50%+核销50%。
- **AIP**：季度激励（KPI比例，上限200%）+ S1 进年度增值池。
- **LIP**（政策原文 RH-HR-A01）：
  `月度绩效奖金 = 考核后部门奖金基数 × 个人绩效系数(0–1.3) × 出勤率`
  - **安全一票否决（硬闸门）**：班组发生损工安全事件 → 全班组当月绩效奖金归 0，管理者连带。
  - **考核后部门奖金基数** = `部门基数 × 部门考核达成`：部门基数由财务测算、可按产线差异化（本签批版统一 1000/月，引擎须支持按部门/产线参数化）；部门考核 = 质量50% + 效率/服务50%，达成→全额、未达→对应维度扣减/归零，**封顶 100%（部门层不设超额上浮）**。
  - **上浮在个人层**：个人绩效系数 0–1.3，凭《现场奖惩单》当日开具、员工签字生效、月度汇总核定。
  - **出勤闸门**：事假致出勤率<80% → 当月无绩效奖金；新员工首月无；最终书面警告→取消当月。

把"员工自己把握收入"落地成可触摸的方向盘（一等功能）：

- 纯前端调用 L2 规则 + L3 纯函数试算，**不落库、不产生承诺**。
- 直接强化期望理论的工具性（instrumentality）透明度。

## 10. 风险护栏（HR/管理前沿理论加固）

| 理论视角 | 风险 | 护栏 |
|---|---|---|
| SDT 关系性 | 体系过度个体化/交易化，侵蚀协作 | **他评维度 + 团队 OKR/协作分**（小权重必存在） |
| 挤出效应 (Deci) | 外在激励挤出高阶专才内在动机 | **第二锚**：学习预算/课题自主/导师身份 |
| 心理契约 (Rousseau) | 职级年度重挣瓦解关系型契约 | 分期灰度、老人过渡（grandfathering）、充分沟通 |
| 双因素 (Herzberg) | 保健因素（基准）不稳变焦虑源 | 基准/职务段变更设**缓冲带**，避免地板剧烈波动 |
| 前景理论 (KT) | 降薪=损失，痛感≈2倍 | **有尊严的滑道**：分期缓冲 + 明确重挣路径 + 框架沟通 |
| 锦标赛理论 | 相对排序破坏合作、打击腰尾部 | 分享分配逻辑公示 + 校准会留痕 |
| Goodhart | 指标决定薪资 → 被操纵 | 量化+定性双复核、区间目标、AI 只聚合证据 |
| 组织公正 | 降职分布可能系统性偏差 | **降职分布公平性审计**（合规+ESG） |
| 可持续绩效 | 高压体系透支组织健康 | 并联**离职率/敬业度/倦怠**监测 |
| 数据治理 | 数据不公→薪酬不公 | 数据血缘、口径冻结、异常审计为一等公民 |

## 13. 数据库 Schema 设计

> 落地规则（项目铁律）：**禁用 `db:push`**；新表用**幂等 DDL**（`CREATE TABLE IF NOT EXISTS` / `ALTER TABLE … ADD COLUMN IF NOT EXISTS`）经 Node 迁移脚本执行；仓储在 `lib/storage/repository.ts` + `memory-store.ts` + `drizzle-store.ts` 三处注册；所有表带 `tenantId` 隔离。全部表前缀 `comp_`。

### 13.1 配置表（policy-as-data，随 `SkillMatrixVersion` 版本化）

- **`comp_job_family`（岗族）**：`id, tenantId, 职能板块(HR|财务|生产|研发|营销), name, 岗类(Ⅰ|Ⅱ|Ⅲ), 序列映射(AIP|MIP|SIP), 可达等级[], versionId`
- **`comp_skill_def`（技能定义 + 定价，HR 动态维护的唯一真源）**：`id, tenantId, familyId→job_family, name, skillWage(技能工资标准), requiredAt(等级[]), 标准来源(案例佐证|市场定价), versionId`
- **`comp_grade_band`（薪酬总表行）**：`id, tenantId, 岗类, 层级, familyId, 岗位学历, 岗位经验区间, 基本工资, skillWageCached(派生缓存·非真源·+重算时间戳), 任务比例, 任务工资标准, 技能级差, 任务级差, 调整级差, 任务档AtoG(jsonb), 对应岗位, 月薪标准, 标准年薪, 占比{base,skill,task}(jsonb), versionId`
  > `skillWageCached` 仅为读性能缓存；技能工资权威值恒以 `Σ comp_skill_def` 实时算，改价后重算刷新。
- **`comp_matrix_version`（版本，§5.2B）**：`id, tenantId, version, effectiveFrom, publishedBy, changelog, status(draft|published|archived)`

### 13.2 员工状态表

- **`comp_employee_grade`（员工当前定位）**：`id, tenantId, employeeId, familyId, 岗类, 当前层级, 岗位学历, 岗位经验, 基本工资(snapshot), 任务档(A–G), effectiveFrom, effectiveTo, certifiedAgainstVersion`

- **`comp_grade_change_log`（述职/PIP/职级变更 + Acknowledgement 链，§6）**：`id, tenantId, employeeId, nodeId, cycle, changeType(知悉|PIP告知|降职生效|职级晋升|任务承接), fromGrade, toGrade, evidenceSnapshot(jsonb), signatureState, signedAt, appealState`

### 13.3 过程与结算表

- **`comp_task_commitment`（B轨承接记录）**：`id, tenantId, employeeId, familyId, cycle, commitmentType(annual|quarterly|half_year|special), fromGear, toGear, taskWageDelta, reason, status(proposed|approved|active|expired|rejected), proposedBy, approvedBy, effectiveFrom, effectiveTo, evidenceSnapshot`
- **`comp_grade_review`（述职/九宫格结果 + 三源分快照）**：`id, tenantId, employeeId, cycle, reviewType(quarterly_checkin|half_year|annual), okrPotentialScore, kpiPerformanceScore, nineBoxRow(潜力1-3), nineBoxCol(绩效1-3), selfScore, peerScore, managerScore, sourceWeights(jsonb), review360CycleId(软引用·复用他评), outcome(promote|hold|watch|pip|demote), snapshot`
- **`comp_monthly_settlement`（月度/周期结算）**：`id, tenantId, employeeId, period, 基本工资, 技能工资, 任务工资, 绩效奖金/分享, 出勤率, 个人系数, 硬闸门标记(安全否决/出勤), 计算依据snapshot(jsonb), status`
- **`comp_budget_pool`（预算池配置，政策 RH-HR-A01）**：`id, tenantId, departmentId(软引用组织架构), period, poolType(lip|department), baseAmount(部门基数·FP&A测算), hardCliff, budgetCeiling, qualityCoefficient, attendanceBasis, params(jsonb), status`

### 13.4 关系、软引用与不变式

- `comp_job_family 1—* comp_skill_def`；`comp_job_family 1—* comp_grade_band`（每层级一行）。
- `employee *—1 comp_job_family`（经 `comp_employee_grade`）；`employee 1—* comp_grade_certification / comp_task_commitment / comp_grade_review`。
- **软引用（不建硬 FK，跨 store 一致性由服务层保证）**：`employeeId→User`、`departmentId→组织架构`、`review360CycleId→review360`（三源他评复用既有 360，不重复造）、`familyId` 与 OKR/KPI subject 的映射由服务层解析。
- **唯一约束**：`comp_grade_band(tenantId,jobClass,level,familyId)`、`comp_monthly_settlement(tenantId,employeeId,period)`、`comp_grade_certification(tenantId,employeeId,skillId,version)`、`comp_grade_review(tenantId,employeeId,cycle,reviewType)`、`comp_budget_pool(tenantId,departmentId,period,poolType)`；`comp_matrix_version` 同租户仅一个 `published`（partial unique）。
- **审计**：改价（`comp_skill_def`）/发布版本/结算，均落既有 `auditLogs`。
- **派生式（非校验闸门）**：`comp_grade_band.skillWageCached := Σ comp_skill_def.skillWage WHERE requiredAt ∋ 层级`——真源恒为 `comp_skill_def`；导入时旧快照差异仅作参考，HR 改价后重算刷新缓存，不阻断。
- **计算式**：`员工技能工资 = Σ 已认证 skillWage`；`月薪 = 基本 + 技能 + 任务(A–G档)`。

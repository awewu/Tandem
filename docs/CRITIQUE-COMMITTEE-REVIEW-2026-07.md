## 2. 委员会审议意见（7 位独立评审）

### 💎 Gem 1 · 行业洞察专家「陈工」（舒适家居行业 20 年）
- **肯定**：三层产品目录 + 两层价格模型抓准行业命门（经销商卖多品牌、SKU 覆盖不全，逼迫开放第三方录入并做成迁移漏斗）。
- **批评**：①"阳谋"纸面成立、渠道现实天真——`Powered by` 豁免易被解读为"藏身份"，信任一旦崩比木马更难恢复；②问诊→报价的专业纵深不足，验收清单仍是模板化固定项、非按实际 BOM 逐设备生成，行业客户会看穿"演示级精算"。
- **裁决**：战略 A / 专业纵深 B-。先证明一个系统（如热水）能真省钱，再谈阳谋迁移。

### 💎 Gem 2 · 代码体系专家「Kenji」（前大厂 Staff Eng）
- **肯定**：28 模块单体、36 迁移无一例外带 RLS、outbox 事务内发事件，地基整洁度属创业期前 5%。
- **批评（最狠一票）**：①测试覆盖是纸糊的——新栈仅 4 个 `.nodetest`，核心资产（quote 价格快照 / design 精算闸 / bim 同步真相源 / RLS 隔离）几无单测，53 guard 检查的是"结构合规"非"逻辑正确"，一次重构就能静默改坏计价而 CI 全绿；②dev 事件链此前完全不通（outbox 永远 pending，本轮才补进程内调度器），暴露关键跨模块路径长期无自动化验证；③仓库在腐烂边缘（`_archive`/`archive`/`legacy`/`experiments`/`tmp-*` 并存）。
- **裁决**：结构 A / 可靠性 C+。补齐核心单测（≥70%）前，不具备"改动安全"资格。

### 💎 Gem 3 · 架构师「Dr. Voss」（多租户 SaaS 架构顾问）
- **肯定**：RLS + 三档隔离 + namespace-extractable 是教科书级；契约优先 + `nestjs-boundary-check` 把边界变红灯，是真护城河。
- **批评**：①愿景与现状鸿沟被宪章文采掩盖——Temporal/Kafka/OLAP/物理分库/CDC 几乎全是目标态、一个未落地，宪章读起来像 D 轮、代码是 Pre-A，对外必须诚实区分"已建成/规划中"；②进程内 `setInterval` 投递是架构级临时方案，多实例会重复/漏投（无分布式锁/租户分片），注释写"生产由 Temporal 驱动"但 Temporal 不存在；③28 模块单体认知负荷接近上限，缺"模块健康度"度量。
- **裁决**：设计 A / 落地 B-。愿景态降级为带时间轴 roadmap；事件投递上真实分布式方案。

### 💎 Gem 4 · 使用者代表「王姐」（苏州经销商门店负责人）
- **肯定**：一个软件从问诊走到施工验收+交付包，不用多系统倒数据，真省事；签单自动生成 BIM 项目好用。
- **批评**：①13 app、经销商台 20 页，一线记不住也不想学，30 岁以上销售为主，且无移动端（customer-portal 才 3 页）；②"设计师台"与"BIM 台"分不清用哪个，两个都要登录培训；③价值感知延迟——签单后同步状态 ~5 秒延迟，客户面前"点了没反应"就是丢单。
- **裁决**：闭环价值 A- / 易用性触达 C。先出移动端极简开单+问诊。

### 💎 Gem 5 · 竞争对手代表「M」（敌意视角）
- **攻击点**：①打"伪中立"——公开质疑母公司身份，把 `Powered by` 豁免包装成"隐瞒利益关系"，引爆经销商信任危机；②打"精算含金量"——用真实工况让 design 精算/验收清单出丑（模板化、devices 提取为 0）；③打"没跑起来的愿景"——要求展示运行中的 Temporal/数仓实例；④打"迁移绑架"——强调数据锁定在集团库。
- **裁决**：对手护城河是工程纪律与闭环完整度（短期难抄）；软肋是信任叙事、精算深度、愿景可信度（三点均可低成本攻击）。

### 💎 Gem 6 · 品牌营销顾问「Lena」（多品牌集团数字营销）
- **肯定**：品牌四层级 + brand-registry 配置化扩张，对标丰田/万豪；"新增品牌=配置"若成立则上线速度是巨大优势。
- **批评**：①中立叙事缺 C 端记忆锚点，问诊入口面临"你是谁、凭什么信你"冷启动，中立放弃了背书红利却无补偿机制；②增长中枢（Nexus Growth）反哺问诊获客的内容管线落地证据薄弱；③三品牌+集团+瑞诺瓦叙事过复杂，需做"减法"。
- **裁决**：品牌架构 A / C 端信任叙事 C+。为瑞诺瓦设计"中立但可信"的背书呈现。

### 💎 Gem 7 · UI/VI/SI 专家「Aria」（设计系统与视觉一致性）
- **肯定**：tokens（品牌皮肤）+ ui（品牌无关组件）+ visual-system 三层分离是世界级设计系统架构；`ui-vi-check`/`rheem-vi-*`/`rysnova-diagnosis-cend-ui-vi-check` 把视觉一致性纳入机器门禁，绝大多数团队做不到。
- **批评**：①设计系统"架构"到位、"内容"存疑，有 token 分层不等于每品牌真有深度 VI；业务工作台是 `dw-*` 功能性工具审美，缺专业软件高级感；②SI（2D-3D 空间交互）是 BIM 灵魂却最薄，`bim-viewer` 存在但 BIM 台仅 4 页，更像"能看模型"非"能深化"；③跨 13 app 无统一交互语言校验，跳转有割裂感。
- **裁决**：设计系统架构 A / 成品视觉·SI 深度 C+。选 1 个旗舰工作台做"高级感+深交互"样板再复制。

## 3. 委员会共识与分歧

**共识（高置信）**
- 最大资产：工程纪律（53 门禁）+ 业务闭环完整度 + 多租户/多品牌架构地基。
- 最大风险：单测缺失导致"改动不安全" + 愿景与现状的诚实度 + 信任叙事脆弱。
- 被反复点名的三软肋：①精算/BIM 专业纵深演示级；②无移动端、13 app 太重；③中立叙事无信任补偿。

**分歧（需决策）**
1. 阳谋要不要更透明？（行业+竞品+营销 vs 宪章战略）建议：不改战略，增加资质背书透明呈现。
2. 先深还是先广？（用户要移动端广度 vs 行业/UI 要精算与旗舰深度）——不能同时做。

**裁决回填（2026-07-10 · 产品负责人）**
1. **阳谋不改**：交付物本质是**瑞合瑞德 / Rhautt 营销赋能工具**，首要受众为**集团经销商 + 集团营销中心**（内部渠道），非不特定外部市场。瑞诺瓦是集团真实技术子公司，故 `Powered by Rysnova` 是**诚实的技术来源署名**，侧面佐证"集团拥有技术子公司"的实力信号——由此弱化竞品"打伪中立"的攻击面。原"中立背书"重定义为"技术来源署名 + 实力佐证呈现"。
2. **深与广都做**：推翻二选一。P2 拆为深广双轨并行/错峰（广轨移动端复用 API 先行 W6–10，深轨 BIM 旗舰 W8–14），同一人承担则退回错峰串行。
> 详见 `docs/RHAUTT-NEXUS-EVOLUTION-PLAN-2026-07.md` §0.1、§3、§6。

## 4. 一句话结论

> 瑞诺瓦的地基（架构+纪律+闭环）已是第一梯队，但现在是一座"结构封顶、精装未做、且缺乏安全绳的大楼"。委员会一致建议：停止扩面，转入"补安全绳（测试）+ 精装一个样板间（热水精算/旗舰工作台）+ 讲清真实楼层（愿景诚实化）"，再谈规模化渠道推广。

# 3D 建模交互问题修复 PRD

## Problem Statement

`4003/viewer` 当前已经具备 3D 构件库、手工构件 CRUD、对象树、构件属性编辑、IFC/GLB 导入和模型查看能力，但实际使用中仍有四类影响建模效率和专业感的问题：

1. 设备清单中暴露了内部技术字段，例如 `manual-*`、`hvac-*`、component ID、关联构件 ID 等。这些字段属于开发和测试阶段信息，不应该出现在正式用户界面。
2. 构件库卡片中仍显示过多小字说明，例如数据来源、BOM code、模板 ID、拖拽提示、测试过程提示等。用户需要的是图标化、专业化、可快速识别的构件工具，而不是调试信息。
3. 当前设备和构件只能放置在平面上，不能放到二楼、空中、墙面高度或吊顶高度，无法满足真实暖通设备安装、管线路由和多楼层建模需求。
4. 拖动建模时鼠标指针和模型位置不一致，存在偏移、滞后或跳动，导致用户不能精确放置和移动构件。
5. 选中模型并修改高度、标高或旋转属性后，3D 视图会失去正常 orbit 查看能力，用户无法继续用鼠标旋转查看模型。这说明属性编辑状态、拖拽状态或输入框焦点可能劫持了视图控制，没有在编辑结束后正确恢复相机控制。

这些问题会让统一 3D 工作台看起来仍像调试工具，而不是面向设计师的建模软件。用户希望界面去掉测试文字，保留专业图标和业务信息，同时支持楼层/标高放置，并让拖拽位置与鼠标严格对齐。

## Solution

围绕 `4003/viewer` 做一次聚焦修复：

1. 清理设备清单的技术字段，只展示设备名称、数量、容量/负荷、系统和必要状态图标。
2. 清理构件库卡片中的技术小字，只保留图标、中文名称和核心尺寸/参数；内部 ID、BOM code、数据来源等信息保留在数据结构或开发调试模式中，不作为正式 UI 展示。
3. 增加楼层、标高、安装高度和高度轴数据支持，使设备和构件可放置到二楼、空中或指定安装高度，并能保存恢复。
4. 修复拖拽坐标映射：鼠标屏幕坐标通过相机射线映射到当前放置平面或标高平面，并使用稳定构件锚点和 pointer offset，保证拖动时模型跟随鼠标。
5. 修复属性编辑后的视图控制恢复：高度、标高、安装高度、旋转等属性输入提交后，必须释放 pointer capture、退出构件拖拽/编辑临时状态，并恢复 OrbitControls 或等价相机控制，使用户能继续旋转、缩放、平移查看模型。

## Product Goals

1. 设备清单成为业务清单，不再暴露 `manual-*`、`hvac-*`、UUID、component ID、BOM code 等技术字段。
2. 构件库成为专业工具面板，主要由图标、中文名称和核心尺寸组成。
3. 用户可以把设备放到二楼、空中、墙面高度、吊顶高度或指定标高。
4. 用户拖动构件时，鼠标和模型位置对齐，避免偏移和跳动。
5. 用户修改高度或旋转属性后，3D 视图仍可立即继续旋转、缩放和平移查看。
6. 新增高度、楼层、拖拽修复后，构件状态仍通过数据库持久化。
7. IFC/GLB 原生导入和查看能力不被破坏。

## Non-Goals

1. 不重做报价算法、BOM 计算规则或设备选型逻辑。
2. 不实现完整 CAD 级吸附、碰撞检测、墙面自动吸附或门窗自动开洞。
3. 不实现完整多楼层建筑结构建模系统，只做本 PRD 需要的楼层/标高/安装高度放置能力。
4. 不编辑导入 IFC/GLB 文件内部几何。
5. 不重写 IFC/GLB loader。
6. 不把 `4001/designer.html` 或旧静态页面重新引入正式流程。

## Hard Constraints

1. `4003/viewer` 仍然是唯一正式 3D 工作台页面。
2. IFC/GLB 导入和查看属于受保护原生能力，本次修复不得破坏：
   - 本地 IFC 打开。
   - 本地 GLB 打开。
   - 后端 artifact/model source 打开。
   - orbit、pan、zoom、fit view。
   - 加载状态和错误提示。
3. 不得修改 IFC/GLB loader 主逻辑；如需让导入源出现在对象树或状态里，只能做外围 UI/metadata 适配。
4. 设备清单和构件库正式 UI 不得显示内部 ID、测试文案、BOM code、seed source、模板 ID、`manual-*`、`hvac-*` 或 UUID 作为主信息。
5. 所有用户可见文案必须使用中文业务表达；图标可以替代说明文字，但不能用测试文案解释功能。
6. 楼层、标高、安装高度、构件位置和拖拽后的新坐标必须通过后端 API 保存，不能只保存在 React state、localStorage 或 Three.js 临时对象中。
7. 新增或修改生产业务 API 必须落在 `/api/v2/*` 方向和目标架构模块中，不能继续堆进旧静态 HTML 或 `server-production.js`。

## Users

1. 设计师：需要从构件库快速选择墙体、门窗、设备、管线，并把设备放到正确楼层和高度。
2. 技术支持工程师：需要检查模型、移动设备、调整安装高度，并确认数据保存后可恢复。
3. 方案顾问：需要看到干净的设备清单和商业摘要，而不是技术 ID。
4. 项目管理人员：需要通过专业界面查看设备、管线和模型状态，不被测试文案干扰。

## User Stories

1. As a designer, I want the equipment list to hide internal component IDs, so that I can read it as a business equipment list.
2. As a sales user, I want equipment cards to show only name, quantity and capacity, so that customer-facing review does not expose technical fields.
3. As a designer, I want component library cards to use icons and Chinese names, so that I can choose components quickly.
4. As a designer, I want BOM codes and seed source text hidden from the main UI, so that the component library feels like a tool palette rather than a debug panel.
5. As a designer, I want to choose floor and installation height before placing equipment, so that I can place a device on the second floor or in the ceiling zone.
6. As a designer, I want selected equipment to expose floor and elevation fields, so that I can correct its height after placement.
7. As a designer, I want drag movement to keep the model under the mouse pointer, so that placement is precise.
8. As a designer, I want dragging to work consistently after zooming, orbiting or resizing the viewport, so that camera state does not cause coordinate drift.
9. As a technical support engineer, I want height and floor values to restore after refresh, so that model review is reliable.
10. As a technical support engineer, I want IFC/GLB import to keep working after these fixes, so that original review workflows are not disrupted.

## Functional Requirements

### Equipment List Cleanup

1. Equipment list cards must not display internal component IDs, UUIDs, `manual-*`, `hvac-*`, API IDs, template IDs or BOM codes.
2. Equipment list cards should display:
   - 设备中文名称
   - 数量
   - 容量/负荷
   - 所属系统
   - 必要状态图标
3. If an equipment row is linked to a component, that link may remain in data but must not be rendered as visible debug text.
4. If debug visibility is needed later, it must be behind an explicit developer/debug mode, not visible by default.
5. Existing equipment summary and BOM/quote handoff data must not lose internal IDs in data payloads; only the formal UI display is cleaned.

### Component Library Cleanup

1. Component cards must prioritize:
   - 图标
   - 中文构件名称
   - 核心尺寸/参数
2. Component cards must not show by default:
   - `来源: seed-global-defaults`
   - seed version/date
   - BOM code such as `WALL_STANDARD`
   - template ID
   - component ID
   - drag/test hints such as `拖入视图放置`
   - long technical metadata
3. Tool rail and category buttons should use icons and concise Chinese labels.
4. Required visible examples:
   - `200mm 标准墙体`
   - `900mm 单开门`
   - `1500mm 标准窗`
   - `客餐厅热区`
5. Technical metadata should remain available to placement and persistence logic through data attributes, state or API payloads, but not as primary UI text.

### Floor, Elevation and Air Placement

1. Component placement must support floor and elevation fields.
2. Equipment placement must support at minimum:
   - 楼层
   - 标高
   - 安装高度
3. Users must be able to place equipment on a non-ground elevation, such as 2F or 3.0m above the first-floor plane.
4. Users must be able to edit selected component height after placement.
5. Height axis must be defined consistently in implementation. If the current Three.js scene uses `y` as vertical axis, use `position.y`; if it uses `z`, use `position.z`. Do not mix axes.
6. Refresh/reopen must restore floor and elevation.
7. BOM/quote summaries should continue using the component even if it is not on the ground plane.
8. Hidden components follow the previously defined summary rule; locked components remain counted unless deleted or excluded by explicit business status.

### Drag Coordinate Alignment

1. Drag placement and drag movement must map mouse pointer to model position through a stable screen-to-world conversion.
2. The interaction should:
   - read current canvas bounding rect
   - convert pointer coordinates to normalized device coordinates
   - cast a ray from the active camera
   - intersect with the current placement plane
   - apply component anchor/pointer offset
   - update component position
3. Placement plane must be height-aware:
   - ground/floor plane for normal placement
   - selected floor/elevation plane for elevated placement
   - future wall plane support must not be blocked by this design
4. Drag start must record pointer offset from the component anchor to avoid jumping.
5. Dragging after zoom, orbit, pan or viewport resize must remain aligned.
6. Component anchor must be explicit:
   - equipment: bottom center or configured placement anchor
   - wall: start point or center, whichever current model uses consistently
   - door/window: installation center or configured host point
   - pipe route: route start or active path point
7. Dragging must update rendered model immediately and save through the existing component update flow.

### Camera Control Recovery After Property Editing

1. Editing height, floor, elevation, installHeight, rotation or position fields must not permanently disable orbit/pan/zoom controls.
2. The UI must distinguish between:
   - typing in a form input
   - dragging a component
   - orbiting/panning the camera
3. While a numeric input is focused, keyboard events may stay in the input, but pointer events on the 3D viewport must still be able to start camera orbit after the input loses focus or the user clicks the viewport.
4. After an input commit, blur, Enter, Escape, save, drag end or pointer up, temporary editing/dragging state must be cleared.
5. If OrbitControls or an equivalent controller is disabled during component drag, it must be re-enabled on pointer up, pointer cancel, drag end and component update completion.
6. If pointer capture is used, it must be released on pointer up/cancel and when the selected component changes.
7. Updating a component's rotation or height must update the component transform only; it must not mutate camera controls or leave the viewport in a modal editing state.
8. Regression coverage must prove that after changing height or rotation, the user can still orbit the camera without refreshing the page.

## Data and Persistence Requirements

1. Component instances must persist floor/elevation/installHeight or equivalent fields.
2. Component instances must keep position and height-axis value consistent with the chosen coordinate system.
3. Existing displayName, dimensions, rotation, visibility, lock state, system key, business metadata and BOM metadata must continue to persist.
4. Device/equipment summaries may retain component IDs internally for linking, but UI rendering must sanitize them.
5. Component catalog templates may retain BOM mapping metadata internally, but UI rendering must hide it by default.
6. Backend validation must reject invalid height, floor, position or malformed geometry values.
7. Cross-tenant/dealer/store persistence boundaries must continue to apply.

## Implementation Decisions

1. Treat UI cleanup as rendering-only changes where possible: do not delete internal IDs from payloads needed for persistence, linking or summaries.
2. Add a presentation adapter for equipment list rows so business fields and internal metadata are separated.
3. Add a presentation adapter for component catalog cards so icons, Chinese names and core parameters are shown while technical metadata remains hidden.
4. Use existing component instance persistence APIs for floor/elevation/installHeight rather than adding a separate local store.
5. Implement drag coordinate mapping in the 3D viewport interaction layer, reusing current camera and raycaster patterns where available.
6. Use a clear vertical-axis convention and document it in code/tests.
7. Add a small interaction state machine or equivalent guarded state for `idle`, `editing-property`, `dragging-component` and `orbiting-camera` so property editing cannot permanently block camera controls.
8. Ensure any disabled camera control state is restored in all completion paths: input blur, save success/failure, pointer up, pointer cancel and component selection change.
9. Preserve existing IFC/GLB code path; add only regression tests around it.

## Testing Decisions

1. Add UI/regression tests proving equipment list does not render internal IDs or technical component IDs.
2. Add component library tests proving seed source, BOM code, template ID and drag/test hints are hidden in normal UI.
3. Add placement tests proving edited floor/elevation/installHeight place equipment above the ground plane.
4. Add persistence tests proving elevated equipment restores after refresh/reopen.
5. Add coordinate tests for screen-to-world conversion or drag helper functions where practical.
6. Add browser/manual acceptance proving dragging stays under the mouse after zoom/orbit/pan.
7. Add interaction regression proving the user can orbit the model after editing height/elevation/installHeight.
8. Add interaction regression proving the user can orbit the model after editing rotation.
9. Re-run existing viewer summary and handoff tests to prove IDs remain in payloads where needed but are not displayed.
10. Re-run model source parity or acceptance tests to prove IFC/GLB import remains usable.
11. Run `designer-workbench` build before claiming completion.

## Acceptance Criteria

1. 设备清单不再显示 `manual-*`、`hvac-*`、UUID、component ID、template ID 或 BOM code。
2. 设备清单仍显示设备名称、数量、容量/负荷和系统信息。
3. 构件库卡片不再显示 seed source、BOM code、模板 ID、拖拽测试提示或长技术小字。
4. 构件库卡片保留图标、中文名称和核心尺寸。
5. 设备可以选择楼层和安装高度后放置到二楼或空中。
6. 选中设备后可以修改楼层/标高/安装高度。
7. 保存并刷新后，设备高度和楼层恢复。
8. 拖拽时模型与鼠标位置对齐，不出现明显偏移、滞后或跳动。
9. 缩放、旋转视角、平移视角或调整窗口后，拖拽坐标仍正确。
10. 修改模型高度、标高、安装高度后，不刷新页面也能继续用鼠标旋转、缩放、平移查看模型。
11. 修改模型旋转属性后，不刷新页面也能继续用鼠标旋转、缩放、平移查看模型。
12. 编辑属性、保存、取消、拖拽结束或切换选中构件后，视图控制状态都能恢复。
13. 设备和管线的 BOM/报价联动不因 UI 清理或高度放置而失效。
14. IFC/GLB 导入和查看能力仍可用。
15. Focused viewer tests 和 `designer-workbench` build 通过。

## Out of Scope

1. 完整楼层管理器和楼板建模。
2. 墙面/吊顶自动吸附。
3. 门窗自动开洞。
4. 多用户协同拖拽。
5. 完整 CAD snapping 和尺寸约束系统。
6. 导入 IFC/GLB 几何编辑。
7. 报价算法重构。

## Further Notes

本 PRD 是 `3d构件建模交互优化.md` 的后续修复 PRD。它不是新增一套大功能，而是清理正式 UI 中残留的测试/技术信息，并补齐手工建模中最基础的高度放置和拖拽精度问题。

实施时要特别注意：不要为了“界面不显示技术字段”而删除后端 payload 中用于关联、BOM、报价、审计的 ID。正确做法是区分数据合同和展示合同，正式 UI 隐藏技术字段，系统内部继续保留必要关联字段。

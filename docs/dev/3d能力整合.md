# 3D 能力整合 PRD

## Problem Statement

当前 Rysnova BIM / 设计能力存在两个割裂入口：

- `http://localhost:4003/viewer` 是现有 React 技术基础，已经承载 IFC/BIM 模型查看能力。
- `http://localhost:4001/rysnova-bim-designer.html` 是深色三栏 3D 暖通设计界面，包含项目参数、建筑参数、系统选择、暖通模型生成、负荷计算、设备清单、交付包、BOM 和报价等设计工作流。

用户现在需要在不同页面之间跳转：设计页面 -> 功能入口页 -> BIM Viewer -> 返回设计页面。这会造成状态割裂、体验割裂、代码重复和后续能力难以继续沉淀。模型生成、模型查看、构件选择、清单报价和交付物本应属于同一个设计工作台上下文，不能继续分散在两个页面、两套 DOM 状态和两套 3D 逻辑中。

本需求要求把正式入口收敛为一个页面：`http://localhost:4003/viewer`。该页面必须以 4003 现有 React 页面为技术基础，以 4001 旧深色页面的视觉和交互为主体，真正合并为一套代码、一套状态、一个页面。旧 `rysnova-bim-designer.html` 迁移后停止继续开发，只保留兼容跳转到 `4003/viewer`。

## Solution

建设统一的 `4003/viewer` 设计页面：在同一 React 页面中承载深色三栏工作台、参数录入、系统选择、3D 暖通模型生成、IFC/GLB 打开、模型查看、构件选择、模型 CRUD、负荷计算、设备清单、2D/BOM/报价入口。

第一阶段目标不是完成所有后续能力，而是先消除入口割裂：

打开 `http://localhost:4003/viewer` 后，用户直接看到旧 4001 页面风格的深色三栏工作台，并且原 4003 Viewer 的 IFC 模型加载能力仍然可用。

统一后的体验路径为：

`设置参数 -> 生成/打开模型 -> 2D 或 3D 编辑 -> 查看设备 -> 查看 BOM 和报价`

而不是：

`设计页面 -> 功能入口页 -> BIM Viewer -> 返回设计页面`

## Product Goals

1. `4003/viewer` 成为 Rysnova BIM / 3D 暖通设计的唯一正式页面。
2. 旧 4001 深色页面的核心视觉结构迁入 React，不再以静态 HTML 继续开发。
3. 保留并强化 4003 Viewer 现有 IFC/BIM 查看能力，不能因为视觉迁移而退化。
4. 形成单一设计状态，支撑项目参数、建筑参数、系统选择、模型、构件、负荷、设备、BOM、报价之间联动。
5. 为后续 2D 转 3D、模型 CRUD、BOM 和报价联动提供清晰产品边界和验收标准。
6. 把 `4001/designer.html` 中已有的 2D 构件能力迁移为 3D 构件库能力，用户可以在 `4003/viewer` 左侧选择墙体、门、窗、房间/区域、暖通设备和管线，并拖拽到 3D 视图中生成真实 3D 构件。
7. 建立构件级 CRUD 能力：用户选中 3D 构件后，可以拖拽移动、调整尺寸、修改属性、删除构件，并且所有变更必须保存到数据库。

## Non-Goals

1. 不做两个页面互相跳转来冒充整合。
2. 不使用 iframe 嵌套旧页面。
3. 不继续在 4001 静态 HTML 页面上开发新能力。
4. P0 不要求一次性完成完整 2D 转 3D、模型 CRUD、正式 BOM 报价联动，但必须预留同一页面内的入口和状态边界。
5. 不改变 Rhautt Comfort 作为集团门户网站的定位；本功能属于 Rysnova BIM / Rhautt Nexus 设计与交付能力。

## Architecture and Persistence Constraints

1. 前端以 `apps/designer-workbench` 的 `4003/viewer` React / Next.js 页面为唯一正式实现入口。
2. 旧 `4001/rysnova-bim-designer.html` 只能保留兼容跳转，不再承载活跃业务状态、模型状态或新功能代码。
3. 后端新增或修改的生产业务能力必须落在目标架构方向：`services/api/src/modules/rysnova-bim` 或相邻 v2 NestJS 模块。
4. 新增生产 API 必须使用 `/api/v2/*` 合同方向；仍需服务遗留 Express 体系时，只能作为兼容层，不得把新业务逻辑继续堆进旧静态页或 `server-production.js`。
5. 所有需要跨会话保留的数据必须保存到数据库，不能只保存在 React state、localStorage、静态 HTML 变量或内存 mock 中。
6. 关系型设计数据、模型记录、CRUD 元数据、项目绑定、版本、状态、租户归属和权限边界优先保存在 PostgreSQL。
7. 大模型文件、IFC/GLB 二进制、生成交付物、设计上下文快照和 AI 对话/报告类文档可按既有架构保存在对象存储或 MongoDB 文档库，但 PostgreSQL 中必须保存可审计的引用、状态和归属记录。
8. 数据写入必须保留 tenant/auth 上下文；模型、BOM、报价、交付包不得出现跨租户读取或无归属保存。
9. 数据库 schema 变更必须通过迁移脚本交付，并配套服务层读写测试或端到端行为测试。
10. 页面中的“估算”数据可以在 P0/P1 使用前端或服务端 deterministic estimate，但一旦被保存、复用到 BOM/报价或客户交付链路，必须写入数据库并标记 estimate/verified 状态。
11. 左侧构件库模板、用户放入模型的构件实例、构件几何、尺寸、位置、旋转、系统归属、业务属性和 BOM 映射元数据必须通过后端 API 保存到 PostgreSQL；不得只写在前端常量、React state、localStorage 或浏览器 IndexedDB 中作为正式数据来源。
12. P1/MVP 可以继续使用 `viewer_design_drafts.generated_model` JSONB 保存构件实例，只要每次新增、编辑、删除都经过 `/api/v2/rysnova-bim/viewer-drafts` 后端接口并能刷新恢复；进入 BOM/报价联动或构件级检索阶段时，必须增加规范化构件实例表，不得长期只依赖大 JSONB 做业务查询。
13. 构件库模板如果只是系统内置默认值，可以由数据库 seed 初始化；如果允许门店、租户或设计师自定义模板，则必须有 PostgreSQL 表承载模板版本和租户归属。
14. 统一页面必须以中文作为主要界面语言，所有用户可见标题、表单、按钮、状态、错误和验收文案必须可正常显示中文。
15. `4003/viewer` 的字体栈必须显式包含中文字体，优先使用系统可用中文字体，例如 `PingFang SC`、`Microsoft YaHei`、`Noto Sans CJK SC`、`Source Han Sans SC`，并保留通用 `sans-serif` fallback。
16. 不得出现中文乱码、编码破损、缺字方框、英文占位文案替代中文业务文案，或用 emoji 代替正式业务图标/标签的情况。
17. 新增或迁移的中文文案文件必须保持 UTF-8 编码；如果遇到 GBK/ANSI 历史文件，编辑前必须先确认编码并说明是否需要转换。

## Users

1. 设计师：输入项目和建筑参数，选择暖通系统，生成或打开模型，并在模型中检查设备和管路。
2. 技术支持工程师：基于签约或待深化项目打开 IFC/GLB/BIM 产物，选择构件，复核碰撞、设备、工程量和交付物状态。
3. 销售 / 方案顾问：在同一页面查看负荷估算、设备清单、BOM 和报价入口，用于客户沟通。
4. 门店 / 管理人员：从统一入口查看项目设计状态、模型状态、清单状态和后续交付链路。

## User Stories

1. As a designer, I want to open `4003/viewer` and see the dark three-column HVAC workbench, so that I can start design work without navigating through multiple pages.
2. As a designer, I want to edit project name and city in the left panel, so that the model, load calculation and deliverables share the same project context.
3. As a designer, I want to edit building area, floors, floor height and room count, so that load calculation and generated 3D layout are based on the same building parameters.
4. As a designer, I want to choose cooling, heating and fresh air systems in one panel, so that model generation and equipment list follow the selected system package.
5. As a designer, I want to generate a 3D HVAC model from the current parameters, so that I can immediately review the building outline, equipment, pipes and system layers.
6. As a technical support engineer, I want to open a local IFC file inside the unified page, so that existing BIM review work remains available.
7. As a technical support engineer, I want to open an approved BIM artifact by artifact ID, so that backend-generated model assets can be reviewed without leaving the design page.
8. As a technical support engineer, I want to open GLB models in the same viewer, so that non-IFC 3D deliverables can be inspected in the same workflow.
9. As a technical support engineer, I want to select model components, so that the right panel can show component metadata, system ownership and related equipment/BOM information.
10. As a designer, I want to toggle 3D, 2D plan and elevation modes from the center viewport controls, so that I can review different drawing views without changing pages.
11. As a designer, I want to toggle pipe and equipment layers, so that I can isolate system problems during review.
12. As a designer, I want to see cooling load and heating load update after parameters change, so that sizing decisions are visible during design.
13. As a designer, I want to see an equipment list derived from the selected systems and current design, so that I can validate equipment count and capacity.
14. As a sales user, I want BOM and quotation entry points in the same page, so that the design result can move directly into commercial discussion.
15. As a project user, I want model CRUD actions in the same page, so that I can create, rename, save, duplicate, archive and reopen design models without losing the current design context.
16. As an implementation agent, I want the old `4001/rysnova-bim-designer.html` to redirect to `4003/viewer`, so that bookmarks remain usable while development continues only on the unified React page.
17. As a product owner, I want visual and functional acceptance to prove IFC loading still works after the migration, so that the first integration milestone is not only a UI copy.
18. As a designer, I want the left panel to switch between project parameters and a 3D component library, so that I can choose what to build without leaving the viewer.
19. As a designer, I want component categories from the old 2D designer to appear as 3D-ready components, so that walls, doors, windows, rooms, HVAC equipment and pipes can be created in the same 3D model.
20. As a designer, I want to drag a wall from the left component library into the 3D viewport, so that I can manually build or adjust the building envelope.
21. As a designer, I want to drag equipment from the component library into the 3D viewport, so that I can place heat pumps, boilers, FCU, radiators, underfloor heating zones, AHU, vents, thermostats and manifolds manually.
22. As a designer, I want to draw or drag pipes directly in the 3D viewport, so that I can manually route refrigerant pipes, air ducts, underfloor loops and condensate pipes.
23. As a designer, I want to select a placed 3D component and edit its length, width, height, thickness, diameter, elevation, position and rotation, so that the model matches the actual design intent.
24. As a designer, I want selected components to be draggable in 3D, so that manual modeling is visual rather than coordinate-only editing.
25. As a designer, I want component edits to be saved to the database and restored after refresh, so that design work is not lost.
26. As a BOM/quote user, I want manually placed equipment and pipes to carry BOM metadata, so that downstream equipment list, BOM and quote can include manually created components.

## Functional Requirements

### Unified Page Shell

1. `4003/viewer` must render a dark three-column workbench as the first screen.
2. The left panel must include project information, building parameters, system selection, primary model generation actions and design progress.
3. The center panel must contain the main 3D/BIM viewport and view controls.
4. The right panel must include load calculation, equipment list, pipe statistics, compliance status, selected component details, and export / deliverable entry points.
5. The page must use React state as the single source of truth for design parameters, generated model state, opened artifact state, selected component state and calculated summaries.

### Model Loading

1. The unified viewer must support local IFC file opening.
2. The unified viewer must support backend artifact loading through existing file-artifact APIs.
3. The unified viewer must add GLB opening support as a first-class model source.
4. Loading a model must not reset project parameters unless the user explicitly starts a new model.
5. Loading status, errors and successful model metadata must be visible inside the unified page.

### 3D HVAC Model Generation

1. The page must generate a 3D HVAC layout from current project, building and system selections.
2. Generated model output must include building outline, room/zone representation, equipment blocks and pipe routes.
3. Cooling, heating and fresh air systems must be represented as separate logical layers.
4. Generated components must carry metadata needed for selection, right-panel details, BOM mapping and later persistence.

### Model Review and Selection

1. Users must be able to orbit, pan, zoom and fit the model view.
2. Users must be able to select a component in the model.
3. Selected component metadata must update the right panel.
4. Users must be able to toggle system layers and visibility for pipes and equipment.
5. IFC/GLB opened models and generated HVAC models must share the same high-level selection state contract, even if their internal geometry loaders differ.

### Model CRUD

1. The unified page must reserve and later implement create, open, save, duplicate, rename, archive and delete model actions.
2. CRUD operations must bind to project context and tenant/auth context.
3. Model records must distinguish generated models, uploaded local models and backend artifact models.
4. Archived or deleted models must not disappear from audit/history requirements if they are tied to customer signoff or contract deliverables.

### 3D Component Library and Manual Modeling

1. The left panel must support page/tab switching at minimum between project/building/system parameters and component library.
2. The component library must migrate the useful component categories from `4001/designer.html` into 3D-ready templates:
   - 墙体：默认墙厚、墙高、长度、材质/结构标签。
   - 门：默认宽度、高度、厚度、安装墙体关系。
   - 窗：默认宽度、高度、离地高度、安装墙体关系。
   - 房间/区域：默认长、宽、高、面积、功能标签。
   - 暖通设备：热泵、壁挂炉、FCU、散热器、地暖盘管区、新风主机、风口、温控器、分集水器等。
   - 管线：冷媒管、风管、地暖管、冷凝水管等。
3. 组件库模板必须包含默认尺寸、系统归属、BOM 映射提示和可编辑属性定义。
4. 用户必须能够从左侧拖拽构件到 3D 视图中放置，放置后生成一个独立构件实例。
5. 用户必须能够选中已放置构件，并在 3D 视图内拖拽移动；MVP 至少支持设备和墙体移动，管线支持端点拖拽或路径点拖拽。
6. 选中构件后，右侧或下方属性编辑区必须显示该构件的可编辑尺寸和业务属性。
7. 属性编辑区必须支持按构件类型显示不同字段：
   - 通用字段：名称、构件类型、系统、楼层/标高、X/Y/Z 位置、旋转角度、状态。
   - 墙体字段：长度、厚度、高度、起点、终点、墙体类型。
   - 门窗字段：宽度、高度、厚度、离地高度、所属墙体。
   - 设备字段：长度、宽度、高度、容量、型号/SKU、安装方式、所属系统。
   - 管线字段：管径、宽度、高度、路径点、长度估算、材质、保温信息、所属系统。
8. 用户修改尺寸、位置或旋转后，3D 模型必须即时更新，并通过后端 API 保存。
9. 手工新增构件必须进入同一模型状态和同一数据库草稿，不得成为只存在于 Three.js 场景里的临时对象。
10. 删除构件必须是构件级删除；如果构件已参与 BOM/报价/交付包，需要软删除或保留审计记录。
11. 鼠标交互必须满足：滚轮缩放、左键/右键视角旋转或平移按既定交互实现，停止拖拽后相机不得自动回到默认视角，默认不得自动转圈。

### 2D-to-3D Relationship

1. 本阶段不以 `4003/floor-plan` 作为 2D 转 3D 的标准来源，也不把该页面作为后续收敛目标；该页面功能暂时不完整，先不进入本 PRD 实施范围。
2. `4003/viewer` 必须同时支持两条路径：
   - 2D 转 3D：以 `4001/designer.html` 的 2D 图纸/构件能力为标准来源，迁移墙、门、窗、房间/区域、设备、管线及其属性，生成 3D 初始模型。
   - 3D 手工建模：直接在 3D 视图里从构件库拖拽创建和编辑模型。
3. 2D 转 3D 生成的构件和 3D 手工创建的构件必须使用同一构件实例数据结构，后续才能进入同一 BOM/报价链路。
4. 2D 转 3D 后的 3D 构件可以继续被选中、拖拽、改尺寸、删除和保存。
5. `4001/designer.html` 仍然不是未来正式产品页面；它只作为 2D 图纸能力和构件属性迁移参考，最终交互必须落在 `4003/viewer`。

### Load Calculation

1. The right panel must calculate and display cooling load and heating load from current building parameters and system selections.
2. Initial implementation may use deterministic local calculation only if clearly marked as estimate.
3. Production calculation must call the project-approved calculation service or v2 API when available.
4. Calculation results must expose inputs, output values and confidence/status for later audit.

### Equipment, BOM and Quote

1. Equipment list must update from generated model components and selected system packages.
2. Equipment rows must support model highlighting or filtering when the linked component exists.
3. BOM entry must receive project context, model context and equipment summary.
4. Quote entry must receive project context, system selection, load result and BOM summary.
5. The page must expose 2D, BOM and quote entry points without forcing users through the old function-entry landing page.

### Legacy Compatibility

1. `4001/rysnova-bim-designer.html` must redirect automatically to `4003/viewer`.
2. The legacy page must not keep a second active implementation of the workbench.
3. The redirect must be a compatibility path only; new feature work belongs to `4003/viewer`.

## State Model

The unified page should maintain one React-side design state with these conceptual sections:

1. `project`: project name, city, project ID, contract ID, opportunity ID when available.
2. `building`: area, floors, floor height, room count, room/zone data when available.
3. `systems`: cooling, heating, fresh air, water, smart-control selections as the design expands.
4. `model`: active source type, local file metadata, artifact ID, generated model ID, GLB/IFC type, load status and version.
5. `selection`: selected component ID, system layer, component type, geometry reference and business metadata.
6. `calculation`: cooling load, heating load, assumptions, standards status and estimate/verified state.
7. `equipment`: equipment rows, capacities, linked component IDs and package metadata.
8. `commercial`: BOM summary, quote summary, deliverable readiness and signoff package references.
9. `componentCatalog`: component template ID, category, display name, default dimensions, editable property schema, system key, BOM mapping hints and tenant/global scope.
10. `componentInstances`: placed component ID, source template ID, type, category, system key, name, geometry, dimensions, position, rotation, elevation, business metadata, BOM metadata, created/updated/deleted status and model version.

## Database Persistence Model

Current implemented database direction already includes:

1. `viewer_design_drafts`: tenant-scoped design draft, project/building/system inputs and generated model JSON.
2. `viewer_model_sources`: tenant-scoped generated/local-upload/artifact model source records, including model type, load status, name, archive/delete state and metadata.
3. `viewer_design_summaries`: tenant-scoped load, equipment, pipe and compliance summaries with estimate/verified trust status.

The 3D component modeling PRD adds these persistence requirements:

1. Every placed 3D component instance must be persisted through the backend before it is considered saved.
2. The persisted component instance must include at least: component ID, draft ID, model source ID when available, tenant ID, project/design/BIM IDs, type, category, system key, name, geometry, dimensions, position, rotation, elevation, business metadata, BOM metadata, status, version, created/updated actor and timestamps.
3. MVP storage can use `viewer_design_drafts.generated_model.components[]` as the persisted component collection, provided component CRUD is only performed through authenticated `/api/v2/rysnova-bim/viewer-drafts/:id/components` APIs and RLS tenant isolation remains enforced.
4. When component instances need independent listing, filtering, audit, BOM rollup, quote rollup or multi-user conflict handling, add a normalized PostgreSQL table such as `viewer_model_components` instead of continuing to query inside JSONB.
5. Component catalog templates must be persisted as seed data or a normalized table when they become editable by tenant/store/user. The template data must include default dimensions and allowed editable properties.
6. Local IFC/GLB file uploads must create or update `viewer_model_sources` records. Binary file storage may live outside PostgreSQL, but PostgreSQL must hold artifact/upload references, ownership, status and model metadata.
7. Calculated loads, equipment summaries, pipe summaries and compliance summaries that feed BOM/quote must be persisted in `viewer_design_summaries` with `trust_status = estimate` or `verified`.
8. All persistence APIs must require auth, tenant context and ownership scope; no unauthenticated local design save endpoint is acceptable for this feature.

## API Contract Requirements

1. Draft save/open/generate/component CRUD must use the v2 Rysnova BIM API direction.
2. Component create/update/delete must be behaviorally idempotent where practical: retrying a save must not create duplicate placed components.
3. API validation must accept the expanded 3D component types required by this PRD, including wall, door, window, room/zone, equipment and pipe/duct route. If the service continues to expose a narrow generated-HVAC enum, it must be expanded before the UI claims these categories are supported.
4. Component geometry validation must reject invalid dimensions, missing path points, negative sizes, malformed IDs and cross-tenant draft/model references.
5. API responses must return the updated model version and component summary so the viewer, equipment list, BOM entry and quote entry use the same saved state.

## Implementation Decisions

1. Use `4003/viewer` as the canonical route and React implementation root.
2. Use the 4001 dark three-column interface as the visual and interaction reference, but migrate behavior into React components and state rather than embedding the old HTML.
3. Keep the shared BIM viewer capability as the model viewing foundation; extend it where necessary for GLB loading and richer component selection.
4. Treat generated HVAC geometry and opened IFC/GLB geometry as different model sources feeding the same page-level model state.
5. Keep existing v2 backend direction for BIM artifacts, signoff package and future CRUD APIs.
6. Do not add new production business routes outside the v2 API direction.
7. Keep compatibility redirect for the old static URL after migration.
8. Keep P0 scoped to visible unification plus IFC loading preservation, then iterate model CRUD, GLB, 2D-to-3D, BOM and quote linkage.
9. Treat `4001/designer.html` as a 2D reference source only. Its construct categories and useful defaults may be migrated, but the unified product surface remains `4003/viewer`.
10. Use database-backed component instances as the contract between manual 3D modeling, generated HVAC modeling, 2D-to-3D conversion, equipment summary, BOM and quote.
11. Do not claim “构件级 CRUD 已完成” unless add, select, move/resize/edit, delete, save, refresh-restore and tenant-scoped backend persistence have all been observed.

## Phased Delivery

### P0: Unified Visual Shell and IFC Preservation

Acceptance:

1. Opening `http://localhost:4003/viewer` shows the dark three-column workbench.
2. The page contains project information, building parameters and system selection controls.
3. The center viewport can load a local IFC file.
4. The center viewport can load an existing backend artifact by artifact ID when available.
5. The right panel shows load/equipment/compliance placeholders or estimates based on the same React state.
6. No iframe is used.
7. `4001/rysnova-bim-designer.html` redirects to `4003/viewer`.

### P1: Generated HVAC Model and Selection

Acceptance:

1. Clicking generate creates a 3D HVAC model from the current parameters.
2. The generated model includes building outline, room/zone geometry, selected-system equipment and pipe routes.
3. Users can select generated model components.
4. The right panel updates selected component metadata.
5. Users can toggle pipe and equipment visibility.

### P2: IFC/GLB Review Parity

Acceptance:

1. The unified viewer supports IFC and GLB local file opening.
2. Backend artifact loading supports model type detection or explicit source metadata.
3. Opened IFC/GLB models expose available component/object metadata to the page-level selection state.
4. Loading errors are visible and recoverable without refreshing the whole page.

### P3: Model CRUD

Acceptance:

1. Users can create, save, reopen, rename, duplicate and archive models.
2. CRUD actions preserve project and tenant context.
3. Saved model metadata includes source type, version, status and linked project identifiers.
4. Archived models remain available where contract/signoff audit requires them.

### P3A: 3D Component Library and Drag-to-Place CRUD

Acceptance:

1. The left panel can switch to a 3D component library.
2. The library exposes wall, door, window, room/zone, HVAC equipment and pipe categories using migrated 2D designer defaults where useful.
3. A user can drag at least wall, equipment and pipe templates into the 3D viewport and create persisted 3D component instances.
4. Selecting a placed component opens a property editor with type-specific dimensions and business fields.
5. Editing length, width, height, thickness, diameter, position, elevation or rotation updates the 3D object.
6. Dragging a selected component in the viewport updates its persisted position; dragging pipe endpoints or path points updates its persisted route.
7. Deleting a selected component removes it from the active model state and saves the deletion through the backend.
8. Refreshing the page and reopening the same draft restores the placed components and their edited dimensions from PostgreSQL-backed persistence.
9. Browser acceptance evidence includes screenshots or recordings proving drag-to-place, select, edit dimensions, delete and refresh-restore.

### P3B: 2D-to-3D Initial Conversion

Acceptance:

1. A 2D drawing/component model migrated from `4001/designer.html` can be converted into a 3D initial model containing walls, doors, windows, rooms/zones, equipment and pipes where 2D data exists.
2. Converted 3D components use the same component instance structure as manually created 3D components.
3. Converted components can be selected, dragged, resized, deleted and saved in the same `4003/viewer` workflow.
4. Conversion results are persisted to the database and can be reopened after refresh.

### P4: 2D, BOM and Quote Linkage

Acceptance:

1. The 2D entry opens the project/model context instead of starting a blank flow.
2. BOM entry receives equipment and quantity summary from the current design state.
3. Quote entry receives system selection, load result and BOM summary.
4. Returning from 2D, BOM or quote preserves the active design/model context.

## Open Questions

1. GLB artifacts should use the same file-artifact API contract as IFC, or a typed model artifact contract under the Rysnova BIM v2 module.
2. Generated HVAC models need a persistence format decision: direct JSON scene graph, GLB export, IFC export, or dual model metadata plus generated artifact.
3. Component selection metadata for uploaded IFC/GLB depends on loader capability; the first implementation may expose coarse object metadata before full BIM property extraction.
4. Model CRUD permissions should align with designer, engineer and project owner roles before production rollout.
5. BOM and quote linkage should define when a result is estimate versus verified, especially before customer signoff.
